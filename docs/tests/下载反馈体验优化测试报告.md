# 下载反馈体验优化测试报告（第五批用户反馈）

> 执行日期：2026-10-05。背景：用户实测发现桌面端点击「下载 .docx」后在保存对话框选定位置，**保存成功/失败无任何提示**，只能自行到目标目录核对文件是否存在。
> 关联：[模板与样式体验优化测试报告.md](模板与样式体验优化测试报告.md)（第四批）；本批在 M6 批量转换已合入的基线上实施。

## 1. 问题与方案

| 项 | 内容 |
|---|---|
| 现象 | 桌面端「下载 .docx」（以及「下载当前模板文件」「导出日志」）经保存对话框落盘后无任何反馈，成功与失败状态不可知 |
| 根因 |（缺陷编号 **D37**）下载走 Chromium 下载管线（`md2word://` attachment），`will-download` 只设置了保存路径策略，**未监听 `DownloadItem` 的 `done` 事件**；日志导出（`handleLogExport`）写盘后同样静默 |
| 方案 | 主进程在下载 `done` 事件（completed/interrupted）与日志导出写盘后，经 `download:feedback` IPC 事件推送结果 → 渲染层复用既有 toast（右上角 2.6s）即时确认。**成功**：「已保存：文件名」（写日志含完整路径）；**失败**：「下载失败：文件名，请重试」；**用户在保存对话框主动取消则不打扰**（cancelled 静默） |
| 覆盖范围 | 三类桌面端保存动作全部覆盖：结果卡「下载 .docx」、「下载当前模板文件」、页脚「导出日志」。网页版无需改动（浏览器自带下载管理提示） |
| 通道 | `download:feedback` IPC 事件（main → renderer，经 contextBridge 白名单订阅 `onDownloadFeedback`，返回退订函数——与 M6 `onConvertProgress` 同一模式） |

## 4. 顺带修复：D33 跨架构 sidecar 错配的真正根源

本批重建安装包时 verify-dist 架构断言再次报错（arm64 包内 pandoc 为 x86_64），追查发现 D33 的真正根源不在构建顺序，而在 `electron-builder.yml`：**dmg target 的 `arch: [arm64, x64]` 列表优先于 CLI `--arm64/--x64` 参数**——每次 mac 构建都会打包双架构，而 extraResources 暂存区只有当前参数准备的那一份 sidecar，后构建的架构必然拿到跨架构 pandoc（此前 `--version` 校验在 Rosetta 下能通过，故未被发现；M6 会话的架构断言使其显形，其 arm64-only 收窄是规避而非修复）。

**修复**：移除 target 级架构列表（`mac.target: - dmg`），架构完全由 CLI/CI 参数决定（release.yml 矩阵 macos-14→`--arm64`、macos-13→`--x64` 天然匹配）；`win.nsis` 保留 `arch: [x64]`（Windows 仅 x64 目标，无此问题）。修复后三产物 verify-dist 11/11×3 全过，且用户已安装的 arm64 应用内 pandoc 实为 x86_64（Rosetta 兜底运行）——**建议用本批新 dmg 重装以获得原生 arm64 sidecar**。
